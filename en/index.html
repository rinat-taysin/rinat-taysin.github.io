How it works and what the agent may not do

Where I started

  • The team is small, and there had been no store release for about 4 months.
  • Testers, managers and marketing posted bugs in a WhatsApp group. Some were about an old build, so the investigations were wasted.
  • Shipping depended on one person. The team measures progress in closed bugs and PRs.
  • I work part-time and can’t also be dispatcher and reviewer. The agents took over dispatching; the decisions stayed with people.

What the agent may not do

  • Money, people, the contract and messages to management need my OK.
  • A question reaches me as one message: options, a recommendation, a deadline and what happens by default. The agent itself does only what can be undone.
  • Without a role, a hook blocks every external command. In WhatsApp the agent writes through a wrapper, pushes with one script that checks for keys, and runs untrusted code only in a container.
  • The “stop” command works without going through the agent.

What it consists of

  • Operator. Reads testers’ findings from WhatsApp, filters out duplicates and bugs from old builds, creates tickets, hands out tasks and takes each PR through to the merge. Tells the testers what to recheck.
  • Release agent. The release plan, store submissions, the evening summary to management.
  • Developer agents. Up to 4 in parallel, each in its own git worktree. Sonnet writes, Opus reviews with veto power, no more than two review rounds.
  • Merge guard. 8 checks: tests, review, trust in the branch. Merging around it is blocked by hooks.
  • Emulator. For UI changes the agent looks for itself, before the testers.
  • Watchdog. Every 5 minutes it checks the agents and the WhatsApp bridge and restarts crashed ones without a model.
  • Releases. EAS from scratch: iOS without a Mac, submission to the App Store and Google Play through the API, a dev → rc → main train.

More facts

Claude Code, Node.js, Linear, Jira, messengers, Windows Task Scheduler

What it consists of, a sample chat, the stack

Where I started

  • I run a mobile app on contract, a partner’s B2B platform and my own AI service.
  • The bottleneck is whoever remembers what matters most. In any department with a stream of requests that is the manager; here it was me.
  • I handed the agents tracker and messenger monitoring, triage of inbox items and voice notes, choosing the next task, reviving stuck work, outage checks, backups and disk cleanup.
  • What works here I carry over into business automation.

System rules

  • Whatever can be computed without an LLM is computed by a script. The model is the lightest one that fits.
  • The system writes first in only five cases: a reply, an outage, a question with a default, a twice-daily summary of facts, and a weekly review.
  • Every open task has an owner agent, and it is the agent that moves it, not me.
  • Agents never see key values. Each one’s permissions are an allow-list in its config.
  • A new rule goes straight into code, a test, a hook or an instruction, and outdated rules are deleted.

What it consists of

  • Operator, code without a model. Listens to the Max messenger, transcribes voice, routes agents’ messages every 15 seconds. At 09:00 it sends one batch of questions with a recommendation and a default.
  • Hub agent. A persistent Claude Code session: answers me and hands big jobs to background workers.
  • Desk agents. One persistent session per project, talking by messages through the hub. At 04:00 they restart into a fresh chat and pick up only the open tasks.
  • Lanes. A Claude session for one Linear task, each in its own git worktree, up to three in parallel.
  • Inbox triage. Dictated notes, voice messages and the Linear Inbox are sorted into trackers without asking me.
  • Priority list. One list across all projects: first tasks under 30 minutes, then those due within 48 hours, then those with consequences. If one project is on fire while I’m working in another, I get a short ping, at most twice a weekday.
  • Stall sweep. Every 30 minutes; it checks whether the task itself moved, not the status mark. Once a week 8 subagents review the week, and I approve the change plan.
  • Watchdog. Every 10 minutes it checks processes, service logins, Docker and disks. It reports a given breakage once a day.
  • Nightly jobs. Document backup to the cloud, phone photos, cleanup to the Recycle Bin, a look at autostart. All code.
  • Tools. 13 shared ones, a separate case study.

More numbers

  • ≈ 11,200 lines of Node.js: 28 scripts, 28 modules, 23 test files.
  • Shared tools: 13 of them, ≈ 20,000 lines, 73 commits since 29 Sep 2026.

How AI fits into the legal process

Where I started

  • A carrier doesn’t know which claim to write, how long to wait, when to go to court or how to calculate the penalty.
  • The platform leads them from the claim through pre-trial settlement to a court order or a lawsuit, and assembles the documents itself.
  • A mistake in an amount or a date costs money. So the model must not invent numbers, see extra personal data, or break the product when it fails.

Where it stands

  • Started 2 Aug 2026, live on vrisk.ru since 21 Sep 2026, after 7 weeks.
  • The client is TEK Antares, Kazan. The pilot is run by the client’s lawyer and its head; staff are joining.
  • 16 releases (v1.0.0 → v1.0.15) in 3 weeks, ~980 commits, 187 ADRs. One developer with Claude AI agents.

Data as of 11 Oct 2026. I don’t publish usage numbers. AI features are switched on by flags as the lawyer checks them.

What I built

First a platform without AI: whatever affects money and deadlines is calculated by code. Then AI on top of it, with three safeguards.

  • Carrier portal. A claim wizard: several demands in one draft, attachments, statuses, publication to the registry.
  • Counterparty registry. A card by tax ID with claim statistics and monitoring.
  • Documents. AI writes the pre-trial claim and the court filing from the case documents. A template assembles the PDF and the mail package; code calculates the penalty and outputs it as a table for the judge.
  • Court. A court order or a lawsuit is filed through “Moi Arbitr”.
  • Service of documents. The pre-trial claim can be sent through e-document services (Diadoc, SBIS, Astral). The service log exports to PDF.
  • Calls. The platform calls the debtor automatically.
  • Data masking. Before a model call, names, phone numbers, emails and passport details become placeholders like [NAME-1], and are restored after the reply. The call log has no texts.
  • Number guard. A reply is accepted only if every amount, date, number and legal article in it appears in the input. Otherwise the document gets the template text.
  • Flags. Each AI feature is switched on separately. If the model is unavailable, the product works without it.
  • Moderation and assistant. For the moderator, AI prepares a checklist with evidence, and the moderator decides. The assistant answers only from the “Disputed situations” cards (pgvector search) and the case data.
  • The rest. Payment reconciliation with the bank, SMS codes, support chat, pricing plans, an admin panel.

One toolkit for all the agents

My own project, since Sep 2026

Problem
Several agent systems need the same chats, tasks, designs and keys. If every project has its own copy, it’s impossible to tell which agent sees what.
What I did
Each tool is written once, and an agent’s permissions live in its config and are enforced by the tool itself. The set includes dictation into any window, a vault of keys the agent can use but never see, and a single login for the messengers.
Result
13 tools for 5 persistent agents. A new project connects with one line in the settings.
  • 13tools in the shared set
  • 5persistent agents on one codebase
  • ≈ 20,000lines: Node.js, PowerShell, Python
  • 73commits since 29 Sep 2026

.NET, Node.js, MCP, Groq

What’s inside: dictation, keys, messengers, trackers, Figma

Where I started

  • The agents work for the mobile app, partners’ projects and my hub. All of them need chats, tasks, design and API keys.
  • Without a shared set, each project gets its own tracker client, its own messenger bridge and its own place for keys. A bug then has to be fixed in every copy.

The main rule

The tools don’t know who is using them: there are no project names or chat lists in the code. An agent arrives with its own config that lists which chats it reads and writes to, and which projects, designs, browser profile and key vault it gets. The tool itself enforces the permissions, so they can’t be bypassed from the command line or through MCP.

What’s inside

  • GroqDictate. I press a hotkey and speak. Groq transcribes, a light model removes slips of the tongue, a dictionary fixes names, and the text lands wherever the cursor is. One .exe on .NET, ~1.8 MB, no installer.
  • Key vault. Keys are stored encrypted, one vault per project, production separate. The master copy is in Bitwarden. An agent can’t show a value: it runs a program through the vault, and the key goes only into that program’s environment.
  • Messaging. Max, WhatsApp and Telegram through one MCP server with a local archive. An agent sees only chats on its allow-list and writes only where it’s allowed.
  • Trackers. Linear and Jira: one library, a CLI and MCP. The filter goes straight into the query, and the answer is checked again. The tool divides the per-key request limit among the agents.
  • Figma. Once a day the tool snapshots the designs to disk, and during the day the agents read them without limits. Each sees only its own files.
  • The rest. A separate Chrome profile for each agent, a pool of accounts for mobile builds, launching persistent sessions.

More numbers

  • 10 test files.
  • GroqDictate is a single ~1.8 MB .exe.
  • All projects’ keys sit in one encrypted place, and agent permissions in one config.
