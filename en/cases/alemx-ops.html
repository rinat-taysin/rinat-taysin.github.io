An AI operator handles the team’s routine; people make the calls

AlemX is an AI super-app live on the App Store and Google Play. I joined as the mobile Product Owner and built an operations agent that triages bugs from the team chat and drives tickets, PRs, reviews, merges and releases. The first store release in 4 months shipped two weeks after I started, and hotfixes now reach the stores in 3 hours.

Role
Mobile Product Owner (contract), designed and built the system
When
Since August 2026
Scale
Product team, 3-person QA team, contractors; app in both stores

The business problem

A small team, and the main store release had been stuck for about 4 months. Bug reports poured into a WhatsApp group from QA, management and marketing. Some were filed against outdated builds, and every one of those wasted an investigation.

Releases depended on a single person. Progress was measured in closed bugs and merged PRs. A part-time Product Owner can’t also be the dispatcher and the reviewer.

The goal: take dispatching off people’s plates (who fixes what, where it stands, what to retest, when it ships) without handing a machine the calls a human is accountable for.

What I built

Two always-on Claude Code agents with plain code around them. The split is simple: anything with a ticket, PR or build number, or anything in the team chat, goes to the operator. Everything else goes to the PO assistant.

  • Operator. Reads the team chat, filters out duplicates and bugs from old builds, files tickets, hands work to coding agents, takes PRs through to merge and tells QA what to retest.
  • PO assistant. Goals, store releases, communication with management.
  • Coding agents in git worktrees. Sonnet writes the code and Opus, the stronger model, reviews it. The author can veto, and review stops after two rounds.
  • Merge guard. Lets a branch into dev only when tests pass, review is done and the branch is trusted. Hooks block any merge that skips it.
  • Watchdog. A script checks the agents and the WhatsApp bridge every 5 minutes and restarts anything that fell over, no model involved.
  • Scheduled passes. Morning plan, a midday sweep for anything forgotten, a Friday weekly summary, an evening retro.
  • Release pipeline. Set up EAS from scratch: iOS builds without a Mac, automatic submission to the App Store and Google Play through their APIs. PRs go to dev only, then ride the dev → rc → main train.

Where the agent can't go alone

  • Money, people, the contract and messages to management need a human OK first.
  • A question to a human comes as one message: options A and B, a recommendation, a deadline and a default. If nobody answers, the agent runs the default only when it can be undone.
  • A session without an assigned role can’t run any external command: hooks block it. The agent posts to WhatsApp only through a wrapper, pushes through a single script that scans changes for secrets, and runs third-party code only in an isolated container.
  • A “stop” command bypasses the agent entirely.

Results

  • 7 mergeson day one with no rollbacks; later up to 21 merges a day
  • 15–29 PRsof bug fixes a day across the team
  • 2 weeksto the first store release in 4 months; then versions 2.0.4 → 2.0.19
  • 3 hoursfrom hotfix to the stores
  • ~25security alerts closed

The investor demo (sign-up, feed, post, paid chat, wallet) ran without a glitch. Along the way I coordinated a 3-person QA team and outside contractors.
